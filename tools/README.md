# Correspondence Tools

This directory contains a small workflow for reviewing CUDA/Metal correspondence
inside `vllm_hook_plugins`. The tools find likely CUDA-side and Metal-side
counterparts, generate an inspection queue, and let a maintainer approve or
reject the proposed mappings before publishing them to `docs/correspondence.md`.

## Files

- `correspondence_scanner.py`: scans the repository and writes deterministic
  candidate pairs to `pending_correspondence.json`.
- `correspondence_review_server.py`: starts a local browser UI for reviewing and
  editing those candidates.
- `verify_correspondence.py`: command-line companion for listing, approving,
  rejecting, and regenerating reviewed correspondence entries.

Generated outputs:

- `pending_correspondence.json`: durable review queue. This file keeps pending,
  approved, and rejected entries.
- `docs/correspondence_review.html`: static review page generated by the scanner.
- `docs/correspondence.md`: maintainer-facing registry generated from approved
  or strong-candidate entries.

## Typical Workflow

From the repository root:

```bash
python3 tools/correspondence_scanner.py
```

The scanner looks under:

- `vllm_hook_plugins/vllm_hook_plugins/workers`
- `vllm_hook_plugins/vllm_hook_plugins/analyzers`
- selected root runtime files such as `hook_llm.py`, `run_utils.py`, and
  `_hook_plugin.py`

For each CUDA-side file, it searches for a likely Metal counterpart, usually in
the sibling `metal/` directory or the root Metal runtime package. It writes the
candidate queue to `pending_correspondence.json` and, unless `--no-html` is
passed, writes a static HTML review page to `docs/correspondence_review.html`.

To preserve existing reviewer edits while rescanning:

```bash
python3 tools/correspondence_scanner.py
```

To rebuild generated comparison rows from current source instead of preserving
the previous matrix:

```bash
python3 tools/correspondence_scanner.py --refresh-matrix
```

## Review UI

Start the local UI with:

```bash
python3 tools/correspondence_review_server.py
```

Then open:

```text
http://127.0.0.1:8765
```

If `pending_correspondence.json` does not exist, the server runs the scanner
first. The UI can display candidate entries, source content, unified diffs, and
comparison rows. Saving changes updates `pending_correspondence.json` and
regenerates `docs/correspondence.md`.

The server supports optional analysis through an OpenAI-compatible local LLM
endpoint at:

```text
http://127.0.0.1:8033
```

That LLM path is optional. The default scanner output remains deterministic and
does not require a model or network access.

You can change the UI bind address or port:

```bash
python3 tools/correspondence_review_server.py --host 127.0.0.1 --port 8765
```

## CLI Review

List entries:

```bash
python3 tools/verify_correspondence.py list
```

Approve an entry and regenerate `docs/correspondence.md`:

```bash
python3 tools/verify_correspondence.py approve probe-hookqk-worker
```

Approve with a replacement note and confidence:

```bash
python3 tools/verify_correspondence.py approve probe-hookqk-worker \
  --confidence high \
  --note "Metal preserves the HookQK capture contract with backend-specific tensor handling."
```

Reject an entry:

```bash
python3 tools/verify_correspondence.py reject science-hallucination-analyzer \
  --reason "No Metal counterpart implements this analyzer."
```

Regenerate the markdown registry from the current pending file:

```bash
python3 tools/verify_correspondence.py regen
```

The CLI accepts custom paths if you want to test against alternate files:

```bash
python3 tools/verify_correspondence.py \
  --pending /tmp/pending_correspondence.json \
  --registry /tmp/correspondence.md \
  list
```

## Data Model

Each pending entry contains:

- `id`: stable command-line identifier.
- `logical_component`: human-readable component name.
- `cuda_path` and `metal_path`: repository-relative paths.
- `status`: usually `pending`, `approved`, `rejected`, or `strong_candidate`.
- `confidence`: `high`, `medium`, or `low`.
- `divergence_note`: maintainer-facing summary of the relationship.
- `comparison_rows`: row-level observations about exact matches, mild matches,
  CUDA-only behavior, Metal-only behavior, dependencies, lifecycle differences,
  artifacts, or risks.
- `summary`: AST-derived classes, functions, imports, and line references for
  each side.

`docs/correspondence.md` includes entries whose top-level status is `approved`
or `strong_candidate`, plus entries with approved or strong-candidate comparison
rows. Rejected comparison rows are omitted from the generated registry.

## Notes

The scanner intentionally avoids making final semantic claims. File pairing,
symbol summaries, diffs, and static review HTML come from repository heuristics.
Treat the output as an inspection queue that still needs maintainer judgment,
especially around tensor shape contracts, artifact schemas, lifecycle behavior,
and platform-specific memory handling.
